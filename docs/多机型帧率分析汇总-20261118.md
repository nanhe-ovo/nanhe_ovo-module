## 二、两台骁龙 8 Elite 逐项分析

### 2.1 SUN · Xiaomi 15 Pro（120 帧，达标但偏热）

- **帧率**：AVG 117.8，5% Low 109.2，Jitter 2.2%，120 帧基本守住；段内有几次掉到 100（约 30 秒、1 分、3 分处），对应帧时间 141 ms 长尖刺。
- **CPU 负载分布偏斜**：
  - CPU 0~5 组使用率 50–65%，频率压在约 2100 MHz；
  - CPU 6~7 组使用率只有 10–45%，频率却钉在 2841 MHz。
  - 即：主力由 0~5 组扛，两颗高频组用不满却维持高频，属于空跑耗电。
- **温度**：SoC 均值 82.9 ℃、峰值 96.5 ℃（≥90 ℃ 仅 2 秒），电池最高 44.1 ℃。4 分 59 秒内 SoC 长期 80 ℃ 以上，余量不大。
- **GPU**：使用率 70–90% 稳定，频率在 170–220 一档内反复摆动（口径存疑，看相对幅度），与 D9400 同类现象——负载平、频率自己跳。
- **DDR**：6374 / 7372 / 8448 三档来回跳，频繁落回 6374 低档。

### 2.2 PINEAPPLE · OPPO Pad 4 Pro（144 帧，不稳）

两次录制同机不同时段：
- 第 3 次（03:49:40）：AVG 110.1、5% Low 51.8、Jitter 17.2%，4m22s 附近有一次掉到接近 0 帧，帧时间峰值 252 ms；SoC 峰值 93.8 ℃。
- 第 4 次（04:34:40）：AVG 119.3、5% Low 91.3、Jitter 7.6%，明显好于第 3 次，但仍有 34.8 的深跌。
- **CPU 表现**：
  - CPU 2~4、5~6 组使用率 60–95%，承接主负载；
  - CPU 7（高频组）使用率 5–85% 大幅摆动，4m22s 一度接近 0，频率在 2100 基线与 3200/3302 突发之间来回；
  - CPU 0~1 组全时段使用率与 cycles 都最低，频率挂在约 1600，负载基本不往这组放。
  - 温度冲高（2m54s–4m22s）与 CPU 7 突发冲高、帧率深跌三者时间重合。
- **GPU**：频率以 220 为基线，2m54s–4m22s 突发到 300–400；使用率 50–90%。
- **DDR**：6389 / 7380 / 8474 三档，两次掉到 4192 的异常低谷。
- 平板机身散热弱于手机，第 3 次已出现 93.8 ℃ 的 SoC 峰值。

### 2.3 “低分组不调用”现象定性

先纠正一个口径：**8 Elite 没有传统 A520 式小核**，Metric 的 CPU 0~1 是频率最低的性能核分组；这里说的“小核不调用”，本质是**低分组（CPU 0~1）拿不到调度负载，负载全部堆到 2~7 组**。判断依据是该组使用率与 cycles 同时最低，而不是只看频率线——频率挂着但有后台任务时，不能算没调用。

可能成因（按可能性排序）：

1. **EAS 能耗偏好**：前台重负载下，调度器倾向把线程放到中高频性能核，低分组只接后台与非关键线程。
2. **uclamp 抬得过高**：前台线程 `cpu.uclamp.min` 被抬高后，调度器拒绝把它回迁到低分组，即使该线程余量很大。
3. **cpuset 亲和掩码**：游戏与渲染线程被圈在性能核集合内，掩码排除了低分组。
4. **厂商/模块频率策略**：中高频簇下限被抬高、低分组没有回落空间，低分组要么空跑要么被边缘化。
5. **观测误判**：只看频率曲线会把“挂低频”误判成“没调用”，需要结合 per-core 使用率与 cycles 一起看。

### 2.4 针对性优化建议（参数 / 调度层面，不写代码）

**排查顺序（先定性，再调参）**
1. `/proc/stat` 看各核 idle 占比，确认 CPU 0~1 是否真的低负载；对照 `scaling_cur_freq` 与 `cpuinfo_top_freq`。
2. 查游戏主线程 / 渲染线程的 `Cpus_allowed_list`（`/proc/<pid>/status`），确认是否被绑在 2~7 组。
3. 看前台 cgroup 的 `cpu.uclamp.min`，判断是否被锁死在高性能档。
4. 对照实验：临时收窄中高频簇上限，观察低分组使用率是否回升——回升说明是 EAS 偏好；不回升说明是亲和掩码或 uclamp 锁死。

**参数建议**
1. **低分组不要钉高频**：CPU 0~1 的 `min_freq` 留回落空间，避免空跑耗电；它的职责是承接后台与轻量线程。
2. **前台 uclamp 适度下调**：给 EAS 留出回迁低分组的余地；但游戏主线程仍建议保留在性能核集合内，不要强行压回低分组。
3. **中核组承接主负载，高频组只做突发**：CPU 2~6 稳住中高频即可；CPU 7 只在瞬时 burst 拉满，平时回落到中高频，削掉 3200 那类尖峰——这同时是给平板降温最直接的手段。
4. **144 帧场景先保 5% Low**：第 3 次 5% Low 51.8 是硬伤，优先把中核频率稳住、限制高频组突发幅度，而不是继续抬高频组上限；目标是 5% Low 回到 90 以上。
5. **DDR 保底**：两台骁龙都频繁下探低档，平板还出现 4192 低谷；把 DDR 下限锁在 6374 / 6389 档，避免带宽突发不足造成帧尖刺。
6. **GPU 窄窗口**：两台 Adreno 频率都在低档摆动，参照 D9400 结论——使用率 80% 以下不必给高频，锁一段窄窗口即可，不要常驻最高档。
7. **温度联动优先于硬锁频**：平板 93.8 ℃、手机 96.5 ℃ 已是硬约束；热到阈值时分档降上限，比把频率钉死更稳。

## 三、与 D9400 分析合并后的最新总结论

### 3.1 三次录制的达标度

- **60 帧（D9400 平板）**：最稳，AVG 63.3、1% Low 59.2、卡帧率 0.40%；问题不在帧，在能效与发热。
- **120 帧（8 Elite 手机）**：达标但偏热，SoC 长期 80 ℃ 以上，高频组空跑。
- **144 帧（8 Elite 平板）**：不稳，两次 Jitter 17.2% / 7.6%，5% Low 51.8 / 91.3，深跌与高频组突发、温度冲高同步。

### 3.2 跨平台共性问题

1. **负载分布偏斜**：要么单核吃满（D9400 的 X925 长期 80–95%），要么低分组闲置、负载堆在中高频组（两台骁龙）。两种偏斜都会造成局部过热与迁移开销。
2. **高频核频率与使用率错配**：8 Elite 的 6~7 组频率钉 2841，使用率只有 10–45%；这是最直接的功耗浪费点。
3. **GPU 频率低档摆动**：三台样本 GPU 使用率都比较平稳，频率却来回跳（D9400 大摆 450↔1250，两台骁龙在低档间小摆）；属调速策略问题，不是负载突变。首选窄窗口锁频。
4. **DDR 频繁下探低档**：天玑保 7488；骁龙两台都需保底，平板的 4192 低谷要优先消掉。
5. **温度 / 功耗是最终硬约束**：D9400 电池 48.1 ℃；8 Elite 手机 SoC 96.5 ℃；平板 SoC 93.8 ℃。频率表现最终都会被热墙收走。

### 3.3 优化优先级（跨平台通用）

1. **绑核与迁移**：先把线程落位理顺（主线程留性能核、轻量线程回低分组、减少跨簇迁移），再谈频率。
2. **频率窗口**：先锁下限稳住基准，再按使用率决定上限；避免高频组空跑钉频。
3. **DDR 保底**：内存带宽档位不低于基准档。
4. **GPU 窄窗口**：使用率富余就压到中低档区间，消除锯齿摆动。
5. **温度联动分档降上限**：热阈值触发后分档回落，不做单点硬限频。

### 3.4 待核实边界

- 两台骁龙为旁路供电，功耗读数为 0 属口径问题，不是节点缺失；如需功耗维度，应改读电源侧（充电器输入）或改用温度/频率等效估算。
- GPU 频率节点口径（分频 / OPP 序号 / 实际 MHz）需在真机 `gpuclk` 节点核对；当前只采信相对摆动。
- 平板 144 帧是否为游戏内原生支持，需确认；若为面板超频帧，深跌可能来自帧率策略而非调度。
- 8 Elite 的物理簇型以真机 `/proc/cpuinfo` 与 `/sys/devices/system/cpu/` 拓扑为准；Metric 的分组是展示口径。
- 本轮为纯分析，未改动模块配置与代码；上述参数建议待真机校准后再落到配置表。

## 五、旁路供电对读数与结论的修正

### 5.1 为什么读数是 0.00 W

旁路供电（bypass charging）时，充电通路绕过电池直接给主板供电，电池既不充也不放，电池侧净电流≈0。Metric 一类工具的功耗估算取自电池电流 × 电压，因此必然读到 0.00 W。

**这不等于整机不耗电**，只是这一路没有被计量。平板在 144 帧下的真实功耗并不比手机低。

### 5.2 交叉证据

两次功耗为 0 的录制，电池最高温度只有 27.0 ℃ 与 26.6 ℃；而能读出 7.64 W 的那次（非旁路），电池最高 44.1 ℃。电池不参与充放，电池温升几乎消失——两条读数互相印证，旁路判断成立。

### 5.3 对结论的四点修正

1. **温度仍然可信，而且更纯粹**：少了充电器与电池的热叠加，93.8 ℃ / 96.5 ℃ 更接近 SoC 自身发热。判定应更严格，不能因为"旁路可能更凉"而放宽。
2. **电池温度不能当散热指标**：26 ℃ 不代表机身凉，只代表电池闲着。
3. **深跌不能归因于供电不足**：旁路下厂商通常会放开更激进的性能策略（没有充电热顾虑），所以 Pad 的 5% Low 51.8 更可能是调度与热策略本身的问题，而非供电受限。
4. **功耗维度改用替代指标**：温度上升斜率、各 OPP 驻留时间、同帧率下的温度增量。同等帧率下温度升得更快，就等价于功耗更高。

## 六、骁龙低分组（俗称小核）高频调动的推测

### 6.1 先把架构口径钉住

骁龙 8 Elite（SM8750）是 2 × Oryon Prime（4.32 GHz）+ 6 × Oryon Performance（3.53 GHz）的全大核架构，**没有 A5xx 类小核**。Metric 里的 CPU 0~1 是最低频策略组，不是物理小核。所谓"小核不调用"，实际是"最低频组不接活得不多、也没被抬到高档"。

### 6.2 四条推测假设

| 假设 | 内容 | 本次样本中的证据 |
|---|---|---|
| H1 天花板被限 | 低组的 `scaling_max_freq` 被 OEM 压到 1.6–2.0 GHz 一带 | Pad 上 CPU 0~1 频率线几乎恒在约 1600 一条水平线，cycles 也最低；若 util 能带动频率，线不会这么平 |
| H2 派活不足 | 低组没有 util 输入，频率自然停在低档 | 使用率与 cycles 双低，且与总负载 60–95% 的高位并存 |
| H3 uclamp 锁死 | 前台线程 `cpu.uclamp.min` 抬太高，低组有空也不接 | 前台重负载期间低组长期空闲，与 EAS 常规行为不符 |
| H4 掩码排除 | cpuset 把游戏/渲染线程圈在性能核集合外 | 需要查 `Cpus_allowed_list` 才能定论，本次未采 |

四条**同时**成立才谈得上"高频调动"：有活可干、util 够高、uclamp 允许、未被掩码排除、温控未压上限。缺任一条都只会得到"挂低频空转"或"根本不接活"。

### 6.3 验证路径（只读，不改模块）

1. `cat /sys/devices/system/cpu/cpu0/cpufreq/{scaling_max_freq,cpuinfo_max_freq,scaling_available_frequencies}` —— 比对天花板是否被人为压低。
2. `cat /sys/devices/system/cpu/cpu0/cpufreq/stats/time_in_state` —— 看是否真的从未驻留过高档。
3. `/proc/<pid>/status` 的 `Cpus_allowed_list` —— 判断掩码。
4. 对照实验：绑一个纯计算负载到 cpu0~1，观察频率是否升到该组 ceiling。升不上去 = H1 或温控；升上去但游戏时不升 = H2/H3/H4。

### 6.4 调动路径（按正当性排序）

**A. 派活式（首选）**
把 RHI 辅助、音频、网络、资源解码这类中等 util 线程迁到低组，让 util 驱动频率自然升到该组 ceiling。副作用最小，也不需要动频率节点。预期：2~6 组负载被削 10–20%，SoC 温度峰值有望降 2–5 ℃。

**B. 抬天花板**
若确认 `scaling_max_freq` 被 OEM 限低，且该组硬件本身支持更高 OPP，才放开到该组上限。注意 8 Elite 的低频子组可能被设计为低功耗用途，硬件层面就不支持高频，强行抬会先撞功耗墙。

**C. 抬下限（仅适合短时 burst）**
`min_freq` 抬到中高档可让低组"看起来高频"，但空转功耗上升，长局只会更快撞热墙。只建议在超频模式的短时窗口使用。

### 6.5 顺带发现：高频组是"跳档"而非逐档

Pad 上 CPU 7 只在约 2100 与 3200/3302 两段之间跳，中间 2400–3000 几乎不驻留。这种二段跳会让帧时间出现尖刺——瞬间拉到 3200 再回落，正是 144 帧下 5% Low 崩到 51.8 的形态之一。

推测：把高频组稳定在 2400–2600 一带（而不是让它去撞 3200），反而更稳、更凉。这与第 2 节建议 3「高频组只做突发」是同一结论的两个侧面。

### 6.6 风险提示

- 低组容量小，重线程迁入会带来新的卡顿，**只迁轻线程**。
- 抬天花板前必须核对 OPP 表与温控联动，否则会变成"高频空跑 + 更快降频"。
- 旁路供电下没有功耗读数兜底，调参只能靠温度与 5% Low 反推，迭代成本更高。
