# 帧率曲线分析 · 2026-11-18 异环 30 分钟实测

> 样本：Metric 2.2.2-release｜平台 D 9400（天玑 9400）｜REDMI K Pad｜OS 4.0.3.0.XAOCNXM
> 游戏：异环 1.5.0｜时长 29m58s｜采样 SurfaceFlinger latency｜双图同一录制（帧率录 + 线程录）

## 一、数据解读

### 1. 帧率：已达标，稳帧是这次的主要结论

| 指标 | 数值 | 判断 |
|---|---|---|
| AVG / MAX / MIN | 63.3 / 66.0 / 51.0 FPS | 锁定 60 帧，均值偏高说明有瞬时超 60（垂直同步抖动） |
| 方差 / 卡帧率 | 0.6 / 0.40% | 极稳，卡帧占比不到半个百分点 |
| 1% Low / 5% Low | 59.2 / 61.2 FPS | 尾部掉帧很浅，最低只到 51 且是单帧 |
| 稳帧指数 | 3.7 ms | 帧间隔抖动可忽略 |
| 帧时间 | MAX 194.3 ms，方差 105.4 | 出现 194ms 的单次长帧，但与 BIG JANK 24 次对应，未形成连续掉帧 |

结论：**帧生成侧没有问题**。60 帧锁得住，30 分钟没有出现趋势性下滑；尾部三两分钟有一次阶段性走低（约 55 帧一带），随后自行恢复。

### 2. 卡顿分布

- SMALL JANK 161 / JANK 107 / BIG JANK 24，30 分钟折算约 0.8 次/分钟大卡顿。
- BIG JANK 集中在 7m30s 前后、22m 之后两段，与 CPU7 掉档、GPU 频率大幅下摆的时间点重合。

### 3. 功耗与温度：真正的约束在这里

- 整机功耗 9.9–14.2 W，均值 12.2 W；**帧能耗 192.58 mW/帧**，对 60 帧平板游戏偏高。
- 电池最高 48.1 °C，曲线从 40 °C 一路爬到 50 °C 并保持——已经贴着平板外壳的舒适上限。
- CPU 温度带在 60–97 °C 之间来回，GPU 稳定在 75–80 °C。
- 也就是说：**性能没到墙，散热和功耗先到墙**。频率曲线里所有"下摆"都能对上温度/功耗节点。

### 4. CPU：大核单点吃满，是这次调度的主要特征

- CPU7（X925）：使用率长期 80–95%，频率以 3600 MHz 为主，但每隔一段掉到 1200–2400，掉档即对应一次卡顿簇。
- CPU4–6（X4 簇）：约 900–1500 MHz，使用率 40–70%，有明显余量。
- CPU0–3（A720 簇）：约 600–1500 MHz，使用率 40–65%，更低。
- 形态是典型"1 颗大核顶着跑、两簇在旁边看"，负载没有横向摊开。

线程侧印证这一点：

| 线程 | 均值/峰值 | 主核 | 迁移次数（30 min） |
|---|---|---|---|
| GameThread | 31.3% / 50.6% | CPU7（98%） | 39 |
| RHIThread | 24.5% / 38.2% | CPU7（53%） | 548 |
| RenderThread | 23.7% / 39.3% | CPU5（27%） | 661 |
| Foreground-worker #1/#0 | 15.1% / 14.3% | CPU6 / CPU4 | 660 / 674 |
| NativeThread | 8.2% | CPU5 | 652 |
| agames.yh.laohu | 6.5% | CPU0 | 725 |

GameThread 绑核质量很好（30 分钟只迁 39 次）；但渲染与后台线程在 CPU4–6 之间来回搬家，约每 2.7 秒一次，属于"没掉帧但白烧调度开销"的程度。

### 5. GPU：频率大幅波动的现场

- 使用率（深蓝）几乎一条直线，稳定在 75–80%。
- 频率（浅蓝）在 **450 ↔ 1250 MHz** 之间做锯齿，周期约 20 秒一个大摆，摆内还有每秒级的快速抖；单个采样点掉到接近 0（约 15 分钟处）。
- 即：**负载是平的，频率是自己跳的**——这排除了"游戏场景负载突变"这条解释，问题出在调频策略侧。

### 6. DDR

- 常态 7488 MHz，间歇顶到 8528，没有长时间压到 6370 的情况。
- 说明内存带宽不是瓶颈，也就解释了为什么降低 GPU 频率并没有带来掉帧——瓶颈不在带宽。

## 二、GPU 频率大幅波动：原因与解决方案

### 2.1 判断路径

先分清三种可能，用一条对照实验就能定性：

1. **下限没锁住**：只设了上限或上限设得高，min 为空，governor 可以自由落到最低档（450）。
2. **调频无迟滞**：升降频门限区间过窄，使用率在 77–80% 附近晃，就在两档之间反复横跳。
3. **外部周期性限频**：平台侧按功耗预算/温度每若干秒重算一次允许频率，曲线上"20 秒一个大摆"正是这种下发周期的形状。

对照做法：把 GPU 上限与下限设成同一个值（如 950/950）跑 2 分钟。若曲线变成一条直线，说明是第 1、2 类；若仍在摆，就是第 3 类（外部限频），此时锁频无效，只能改温度/功耗策略。

另：15 分钟处那个掉到 0 的单点，是采样或 GPU 重新初始化的读数，不是真实掉频，不必当作故障。

### 2.2 解决方案（按代价从低到高）

**方案 A｜窄窗口锁频（推荐首选）**
不要锁单点，锁一段窄窗口（如 900–1050）。既消掉 450 那一侧的大下摆，又给平台留一点自调空间，温度压力最小。本次样本 GPU 使用率只有 75–80%，属于明显富余，压到 900–1050 完全不影响 60 帧。

**方案 B｜频率固定 + 温度联动**
把 GPU 固定在 950 左右，同时挂一条温度规则：CPU/GPU 温度超过阈值时把上限降一档（1000 → 900 → 800），而不是让它在 450 和 1250 之间自由落体。这样既没有锯齿，也不会在热墙上突然限死。

**方案 C｜打开迟滞**
- 天玑：调 governor 的 upthreshold 与 down-differential，让升降频之间留 10–15% 的死区。
- 骁龙：devfreq 侧调 `sampling_rate` 与 `up/down threshold`，把采样周期从默认值拉长到 50–100 ms。
- Exynos/Mali：`scaling_governor` 用 interactive，并把 `freq_step` 从 5–10% 收窄。
作用是把"每秒级抖动"抹平，20 秒级的大摆要配合方案 A/B 才治得住。

**方案 D｜先治功耗，再治频率**
本次 12.2 W 均值 + 48 °C 电池温度，本身就在触发平台降频。把 CPU7 从 3600 常驻降到 3300、或允许 GameThread 在两颗大核间轮转，整机功耗能先降 1–1.5 W，GPU 的摆动幅度会自然收敛。**顺序上，先降 CPU 单点压力，再谈锁 GPU，性价比更高。**

**不建议做的**
- 把 GPU 上限也拉到 1250 常驻：温度会更快撞墙，反而换来更频繁的硬限频。
- 只写 min 不写 max：governor 照样往上冲，锯齿仍在，只是下沿被抬高。
- 硬写只读节点（天玑一批 scaling_* 节点是只读/SELinux 限制）：写不进去只会刷日志，本次日志里那条 `policy7 scaling_min_freq Permission denied` 就是这类，应当识别后跳过而不是反复重试。

### 2.3 验收标准

改完之后用同一录制条件复测：GPU 频率曲线的高低差应落在 150 MHz 以内，使用率仍平；1% Low 不低于 59，帧能耗应低于 190 mW/帧。

## 三、全平台优化建议

以下按平台族给，参数形态通用（上下限、迟滞、绑核、DDR 保底、刷新率），具体数值需真机校准。

### 3.1 通用五条（所有机型都适用）

1. **先锁下限，再谈上限**。多数"降频"投诉来自下限为空，而非上限太低。
2. **窗口优于单点**。锁 900–1050 比锁 950 更耐温、更少触发硬限频。
3. **只读节点一律跳过并记日志**，不要重试，更不要回滚到上一状态造成二次写入。
4. **温度/功耗门限优先于频率**。频率是结果，功耗预算才是原因。
5. **绑核优先于抬频**。GameThread 绑大核 + 允许一颗中核协同，比把大核顶到最高频更省功耗。

### 3.2 天玑（本次实测平台）

- CPU：GameThread 绑 X925（CPU7），把 X4 簇留一颗给 RHIThread；A720 簇设一个不低的下限（≥900），避免渲染线程掉进低频后又被拉回产生迁移。
- GPU：方案 A 的 900–1050 窄窗口；使用率 80% 以下不必给 1200+。
- DDR：保 7488 基频，禁止长时间落到 6370；8533 只做突发。
- 刷新率：平板 60 帧场景不需要 120 Hz，取消静止降频即可，别开高档。

### 3.3 骁龙 8 系

- 用 `kgsl-3d0` 的 min/max 与 `gpu_available_frequencies` 做窄窗口，别直接写 OPP 序号。
- schedutil 的 rate_limit 调到 5000–10000 us，减少每秒级抖动。
- 8 Elite 及更新平台普遍有 GKI/LKM 限制，写频率前先判可写性，只读就退回 uclamp。

### 3.4 麒麟

- DVFS 表档位少、节点受 SELinux 限制多，硬写成功率低。
- 优先用 sched 的 uclamp（min/max perf）表达意图，让内核自己选频；只在小核簇做下限保护。

### 3.5 Exynos

- 簇型差异极大（部分平台小核簇定义与常规不同），配置项要按簇实测后再定。
- GPU（Mali）用 interactive governor，收窄 `freq_step`，别用 performance 常驻。

### 3.6 Tensor

- 热墙来得早，锁频意义有限；建议按功耗预算限 TDP，让频率自然跟随。
- 相机/AI 后台线程活跃，绑核时给渲染线程留出专用核。

### 3.7 展锐 / 入门平台

- 频率档本来就少，锁频收益低；重点放在 DDR 保底与刷新率，以及避免后台线程抢占小核。

### 3.8 分场景建议

| 场景 | 优先动作 |
|---|---|
| 60 帧锁帧手游（本次） | GPU 窄窗口 + CPU7 降一档 + 取消静止降频 |
| 高帧率（90/120） | 先保 GPU 下限，再放宽上限；CPU 用双大核并行 |
| 长时间挂机/低负载 | 关高档刷新率，GPU 降到最低可写档，不动上限 |
| 已发热降频 | 改温度联动分档降上限，不要锁死单点 |

## 四、结论

1. 本次 30 分钟实测**帧率达标**：AVG 63.3、1% Low 59.2、卡帧率 0.40%，没有趋势性衰减。
2. 真正的短板是**能效与散热**：12.2 W 均值、192.58 mW/帧、电池 48 °C。
3. GPU 频率锯齿（450↔1250）是频率策略问题，不是负载问题；优先用 900–1050 窄窗口，其次温度联动，最后才考虑调迟滞。
4. CPU 侧最大浪费是 X925 单核 80–95% 常驻，横向摊开负载比继续抬频更划算。
5. 天玑平台一批限频节点只读，属设计如此，识别跳过即可，不应视为故障。
