## 二、共性问题（四段横看）

### 1. 帧率与负载不匹配的两种形态

- **A（天玑）**：负载平、频率自己跳。GPU usage 75–80%，频率却在 450–1250 之间做 20 秒级大摆 + 每秒级抖动。
- **B/C/D（骁龙）**：反过来，GPU usage 50–90% 不低，频率却被压在 160–300 MHz 低档，只偶发抬到 340–600。队列排满后帧时间尖刺（B 448 ms、D 252 ms、C 141 ms）。

两边都是 DVFS 与负载脱钩，只是方向相反：天玑是**上摆过度**，骁龙是**下压不足**。

### 2. CPU 负载分布不均，弱簇被晾在一边

- A：X925 单核 80–95% 顶着跑，两个中簇 40–70% 有余量。
- B/D：CPU0-1（8 Elite 上最弱的中核簇）频率平线停在 1600–1800，cycles 占比最低；任务优先落在 CPU2-7。
- C：钉频后出现反向——Prime（CPU6-7）使用率 10–40% 末尾趋近 0，CPU0-5 反而扛 50–65%。说明**固定频率不等于调度派发**，钉频解决不了负载倾斜。

### 3. 热是掉帧的直接扳机

- D 机 2m54–4m22s 升到 93.8 °C，Prime 被压到近 0 使用率、频率 800，FPS 直接出现 0 帧；降温后恢复。
- C 机均值已 82.9 °C、峰值 96.5 °C，7.64 W 功耗下仍贴热墙，只是 120 帧目标不高才没有崩。
- A 机 30 分钟 12.2 W、电池 48 °C，属于性能未到墙、散热先到墙。

### 4. DDR 波动不是主因，但有风险点

A 机 7488 常态、8533 突发，健康；D 机两次跌到 4192，属于带宽潜在风险；C 机 6374–8448 尚可。

## 三、骁龙「弱簇不被调用」专项分析

### 3.1 现象定性

骁龙 8 Elite 没有传统小核，CPU0-1 是最弱中核簇。三段记录里能看到的事实是：

1. 该簇频率长期停在低档平线（1600–1800），没有随负载抬起；
2. 逐核 cycles 低于其它簇，说明不是「频率低但任务在跑」，而是任务本身被少派；
3. Prime 簇使用率波动很大（B/D 10–50%，C 末尾趋近 0），负载在簇间来回摆，没有稳定的分工。

### 3.2 成因（按可能性排序）

1. **EAS 能耗模型偏向大核**：延迟敏感的游戏线程在容量评估阶段就被分到中/大核，弱核拿不到可运行队列；后台 worker 也被跟着拉走。
2. **钉频只改频率、不改调度**：把弱簇 min/max 钉在某一档，EAS 仍然按能耗模型选核，弱核保持低频空转——C 机钉频后 Prime 闲置就是反证。
3. **uclamp / boost 上移**：游戏线程被 boost 后容量标记抬高，EAS 更锁定大核，弱簇接不到降级任务。
4. **亲和性掩码**：部分渲染/ worker 线程被绑在中、大核集合内，弱核不在候选名单。
5. **热限回摆**：D 机热触发后大核先被压，负载回摆时已经掉帧，不是健康的均衡。

### 3.3 只读排查步骤（不改配置先定性）

1. 逐核统计：读游戏进程各线程 `/proc/<pid>/stat` 累计 jiffies 与每核当前使用率、频率，算 cycles 占比，确认是「没派任务」还是「派了但频率低」。
2. 调度证据：`/proc/schedstat`、`sched_debug` 看负载均衡次数与迁移动向，确认任务是否在簇间反复横跳。
3. 任务标记：看线程 affinity 掩码与 uclamp min/max 标记，判断是否被排除出弱核簇。
4. 调频器：确认 governor 是 schedutil 还是 interactive，读可用频率表与当前上下限。

### 3.4 针对性优化（策略层，参数需真机校准）

**CPU 分工，而不是平均抬频**

- GameThread / 主逻辑线程：绑 Prime 簇，保留峰值余量。
- RHIThread / RenderThread / 前台 worker：放中簇，按每核 cycles 均摊。
- 后台杂项、NativeThread、后台 worker：放弱簇，把负载填进去，而不是让弱核空转。
- 手段优先用亲和性与 uclamp 容量标记，不要靠全簇钉频。

**弱簇频率**

- 弱簇下限抬一档（比当前平线高半档到一档），让 EAS 看到可用容量；不要钉满，避免空载耗电。
- 中簇保持 schedutil 动态跟随，rate_limit 5–10 ms，减少每秒级抖动。
- Prime 保留峰值档，热触发时先降 Prime 上限一档，而不是直接压到 800。

**GPU（本轮骁龙三机更突出的问题）**

- 现状是高频低用：usage 50–90% 却跑 160–300 MHz。把 GPU 下限抬到 400–500 MHz 的窄窗口，上限暂不放宽。
- 检查 kgsl devfreq 的升降频门限与功耗预算，确认是不是被 power cap 压在低档；门限之间留 10–15% 迟滞。
- 温度联动：SOC 越过阈值时分档降 GPU 上限，不要让频率在最低档和中档之间反复跳。

**热与 DDR**

- D 机型：93.8 °C 是硬墙，提前在 85 °C 附近降 Prime/GPU 上限，避免撞墙后的 0 帧。
- C 机型：均值 82.9 °C 已偏热，先压 Prime 常驻频率与 GPU 下限，把整机功耗从 7.64 W 往下收。
- DDR 保底不低于 6370 一档，避免出现 D 机 4192 那类深跌。

## 四、与上一轮天玑记录的合并结论

1. **帧稳不稳，看 1% Low 和帧时间尖刺，不看平均帧**。A 机均值 63.3 很稳但仍有 24 次 BIG JANK；D 机均值 110 但 5% Low 只有 51.8、出现 0 帧，是四段里最差的一段。
2. **调度问题分两类**：负载倾斜（A 单核顶、B/D 弱簇闲置、C Prime 闲置）和 DVFS 脱钩（A 上摆、B/C/D 下压）。修法不同：前者靠绑核与容量标记，后者靠频率窗口与迟滞。
3. **GPU 是本轮骁龙三机的共同短板**，优先级高于继续抬 CPU。usage 已经不低，频率却在最低档，队列堆积直接表现为帧时间尖刺。
4. **温度决定能撑多久**：A 机靠 30 分钟慢慢热上来，D 机 3 分钟撞墙崩帧，C 机全程贴墙。长时场景必须有温度联动的分档降频，而不是一路放开。
5. **钉频是手段不是结论**：C 机钉频后簇间使用率仍然不均，说明写死上下限不能替代调度均衡；先把线程分工理顺，再决定各簇留什么频率窗口。
6. **只读/受限节点照旧跳过**：天玑一批 scaling_* 节点只读，写不进去记日志即可；骁龙 kgsl/devfreq 节点先判可写性，失败回滚不二次重试。

## 五、待真机复核项

- PINEAPPLE / SUN 平台号与簇型映射，确认 CPU0-1、CPU2-4、CPU5-6、CPU7 各自归属。
- B、D 两段功耗读数缺失，补测时接功耗计或读电池功率节点。
- GPU 下限抬到 400–500 后的温度与帧时间变化，需同一游戏、同一画质复测。
- 弱簇填充后台线程后，确认没有把前台线程挤回大核造成二次倾斜。
