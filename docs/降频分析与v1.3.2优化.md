# 降频表现分析与 v1.3.2 优化说明

> 分析对象：Redmi K Pad（D 9400 / mt6991，OS 4.0.3.0.XAOCNXM）上 29 分 58 秒的 Metric 帧率与线程记录。
> 结论与改动：v1.3.2 新增 `mtd9400` 平台配置，并在回退模板时明确告知「uperf 不接管频率」。

## 一、两张图里读到了什么

**帧率记录（29m58s）**

| 指标 | 数值 | 含义 |
| --- | --- | --- |
| FPS MAX / MIN / AVG | 65.0 / 49.9 / 61.3 | 平均接近满帧，但存在掉到 50 附近的时段 |
| 1% Low / 5% Low | 55.2 / 57.5 | 最低 1% 帧并不难看，说明不是长时间崩帧 |
| 大卡顿 / 卡顿率 | 27 次 / 4.9% | 卡顿是**尖峰型**，不是持续掉帧 |
| Frame Time 最大 | 1594ms（方差 9.5） | 有单帧异常长，通常是调度/内存抖动 |
| CPU 温度 AVG | 43.6℃ | 温度不高，**不是热降频** |
| 功耗 AVG | -10.18W | 平板功耗正常 |

**曲线特征**

- **CPU 频率**：八个核在 400MHz 与各自最高档之间高频来回，周期只有几百毫秒 —— 典型的「负载一低就立刻砸到最低档」。
- **DDR 频率**：在 1066MHz 与 8533MHz 之间反复跳，几乎每个采样点都在变 —— 内存没有保底频率。
- **GPU 频率**：在 1599MHz 与 600MHz 附近往返，和掉帧尖峰对得上。
- **线程记录**：GameThread 60.0%、RenderThread 46.6%、RHIThread 43.4%，但 30 分钟内 GameThread 迁移 536 次、RenderThread 669 次、RHIThread 663 次，最多的一条到 771 次 —— 线程在 cluster 之间被反复搬运。

**判断**：温度不高、1% Low 不低，说明瓶颈不是散热，而是**频率/内存/线程的频繁切换**——每次从最低档拉回高频都要几十毫秒，正好对应那 27 次大卡顿与 1594ms 的异常帧。

## 二、模块这边查到的原因

模块的安装器按 `ro.board.platform` 选配置：

```
mt6991 → mtd9400
```

但 `module/config/` 里**没有 `mtd9400.json`**。于是安装时回退到 `template.json`，而模板里：

```json
"cpu": { "enable": true, "powerModel": [] }
```

`powerModel` 是空的 —— **uperf 没有功耗模型就不会接管 CPU 频率**，DDR 的 `ddrMin` 也没有设备节点，等于模块只做了「压平厂商调度」，频率完全交给系统 DVFS。系统 DVFS 的策略就是「能低就低」，于是出现图里的锯齿。

同类缺口不止一个：`mtd930`、`mtd1100`、`mtd6000` 等映射名也没有对应文件，只是这次正好落在你的 D9400 上。

## 三、v1.3.2 改了什么

1. **新增 `module/config/mtd9400.json`**（Dimensity 9400 / mt6991）
   - 三段功耗模型按真机拓扑写：4×A7xx（2.4GHz）、3×X4（3.3GHz）、1×X925（3.63GHz），`typicalFreq` / `sweetFreq` / `plainFreq` 按同代平台（D9200）比例换算，不再留空。
   - `presets` 带 DDR 保底：均衡 3.2GB/s、省电 2.667GB/s、性能/极速 5.5GB/s —— 直接针对图里 1066↔8533 的方波。
   - 保留原配置里的 cpuset、前台/后台分组与触摸场景 margin，不改系统默认调度器。
2. **回退模板时写日志**：安装器发现没匹配到平台配置，会在 `/data/adb/nanhe_ovo/log.txt` 记一条 `warn config`，写明 platform/board 与「uperf 不会接管频率」，面板「关于 → 运行日志」直接能看到，不用再猜。
3. **安装提示更明确**：回退模板时提示「该模板不含功耗模型，uperf 不会接管 CPU 频率」，避免把「模块没生效」误判成「模块在降频」。
4. **测试补三条**：mt6991 必须命中 `mtd9400.json`、配置名落盘为 `mtd9400`、配置内确实含 3.63GHz 的功耗模型点。POSIX 套件从 207 条增到 210 条，全绿。

## 四、刷入后怎么验证

1. 重刷 `nanhe_ovo-v1.3.2-20261122.zip` → 重启。
2. 面板「关于」里的「平台配置」应显示 `mtd9400`（不再是 `template`）。
3. 再录一段同样的 Metric：
   - CPU 频率锯齿应保留「有负载才升」的形态，但**低频停留时间变短**；
   - DDR 不再长期趴在 1066MHz；
   - 大卡顿次数应低于这次的 27 次。
4. 若某机型反而更耗电或更热，面板「频率 → 恢复开机频率」可立即还原本次开机的边界；想彻底退回，删掉 `/data/adb/nanhe_ovo/device_config.txt` 并换回 `template.json` 亦可。

## 五、必须说清的边界

- `mtd9400.json` 的功耗模型是按 D9200 同代参数与 D9400 公开频率**推算**的，不是联发科官方调参表；真机表现需要你用上面第 3 步复测。
- 这份配置只动 CPU 功耗模型、presets 的 margin 与 DDR 保底，不碰电压、不锁最大频率，也不改 `scaling_governor`。
- 线程迁移次数多属于内核调度行为，模块不改 `sched` 亲和性（`modules.sched.enable=false`）；要压迁移需要另开 affinity 方案，不在这次改动范围内。
- 这次没有真机，验证仅到「配置能被安装器正确选中 + JSON 结构合法 + 210 条后端断言」这一层。
